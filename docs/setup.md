# Установка и обновление Pi Mobile 0.6.000

## Обновление Android

Установить `Pi-Mobile-0.6.000.apk` поверх старой версии без удаления приложения: подпись сохранена, настройки подключения остаются. Это первая версия с обновлятором. Дальше приложение проверяет GitHub при открытии каталога (не чаще раза в6 часов); вручную — Settings → Check for updates. Загрузка начинается после согласия, APK проходит проверки размера, SHA256 и подписи. Android попросит разрешить установку из Pi Mobile и подтвердить обновление. Без подтверждения установка не выполняется.

Для условной загрузки кешированных диалогов и карточек usage обновить также gateway до0.6.000. Старый gateway совместим, но передаёт полные снимки и не отдаёт usage. Перезапускать только relay, не работающие Pi. Workflows/субагенты пока не визуализируются отдельными карточками.

## Требования

- macOS либо Linux с пользовательской desktop-сессией и **Orca IDE**, установленным Pi (`@earendil-works/pi-coding-agent`), Node ≥22.18, npm, Python3.
- Orca должна иметь хотя бы одно локальное рабочее пространство. Запустить Orca обычным способом из desktop-сессии. Gateway сам не запускает GUI и не создаёт рабочие репозитории.
- На Linux CLI называется `orca-ide` либо задаётся абсолютным `ORCA_CLI_COMMAND`. **Не использовать системную команду `orca`: это может быть GNOME screen reader.**
- Для телефона — HTTPS с WebSocket, напрямую через свой reverse proxy или Tailscale Funnel. Node-порт не открывать наружу.

Не копировать API-ключи, настройки моделей и токен другого пользователя. Расширение использует Pi того пользователя, под которым установлен relay.

## Общая установка

Клонировать репозиторий в постоянную папку и выполнять команды от обычного пользователя, не root:

```sh
cd /path/to/pi-mobile
npm ci
pi install "$PWD"
npm test
```

`pi install` регистрирует локальный пакет расширения. Папку после этого не перемещать без повторной регистрации. Если тесты не находят установленный Pi, добавить каталог бинарника `pi` в PATH; при нестандартной установке задать `PI_HOST_ROOT` абсолютным путём к установленному пакету Pi.

### macOS

```sh
./scripts/install-service.sh
curl --fail http://127.0.0.1:8788/health
```

LaunchAgent `ru.billyhargrove.pi-mobile`, логи `~/Library/Logs/PiMobile/gateway*.log`. Скрипт рассчитан на PATH Homebrew и `/usr/local/bin`; при другой установке скорректировать EnvironmentVariables в plist. Relay работает после входа пользователя; спящий Mac недоступен.

Для HTTPS через Caddy: сначала заменить домен в `server/Caddyfile` на свой, настроить DNS и перенаправление TCP80/443, установить Caddy, затем `./scripts/install-https.sh`. **Не запускать этот скрипт с чужим доменом из примера.** Если HTTPS уже обслуживается существующим proxy, добавить только свой маршрут; не перезаписывать другие сервисы.

### Linux

Убедиться, что PATH содержит Node, Pi и Orca CLI, например:

```sh
export PATH="$HOME/.local/bin:$HOME/.npm-global/bin:$PATH"
export ORCA_CLI_COMMAND="$HOME/.local/bin/orca-ide"
./scripts/install-service-linux.sh
systemctl --user status pi-mobile.service
curl --fail http://127.0.0.1:8788/health
```

Скрипт сохраняет резервную копию существующего unit, устанавливает `~/.config/systemd/user/pi-mobile.service`, включает и запускает только relay. **Не меняет Tailscale, не запускает/перезагружает Pi.** Логи: `journalctl --user -u pi-mobile.service -n 100`.

PATH и путь Node фиксируются при установке. После смены Node/Pi/CLI повторить установку unit. По умолчанию PID Orca проверяется через `${XDG_CONFIG_HOME:-$HOME/.config}/orca/orca-runtime.json`; при другом пути задать `PI_MOBILE_ORCA_RUNTIME_FILE` перед установкой. Отсутствие живого PID даёт ошибку inventory, а не бесконечные попытки запуска Electron.

Unit запускается в user manager; не гарантирует запуск Orca после logout/reboot. Настройка desktop-autostart отдельно, с учётом Wayland/X11. Не запускать многократно `orca-ide open` из SSH, если desktop не готов.

## HTTPS через Tailscale Funnel (Linux или Mac)

Сначала проверить существующие `tailscale funnel status` / `tailscale serve status`. Не выполнять reset: другие порты/маршруты могут обслуживать SSH и приложения.

Пример отдельного mount на уже разрешённом Funnel-порту8443:

```sh
tailscale funnel --bg --https=8443 --set-path=/pi-mobile http://127.0.0.1:8788
```

Для изменения Tailscale могут требоваться права оператора или sudo. URL телефона: `https://<имя-хоста>.<tailnet>.ts.net:8443/pi-mobile`. Funnel публикует маршрут в интернете, поэтому **bearer-токен всё равно обязателен**. В этой конфигурации Funnel срезает `/pi-mobile`, и `PI_MOBILE_BASE_PATH` у relay остаётся пустым.

Если другой proxy **сохраняет** префикс, задать relay `PI_MOBILE_BASE_PATH=/pi-mobile`; он применится к REST и WSS. Не задавать префикс дважды. Проверить публичные `<URL>/health` (200), `<URL>/api/catalog` без токена (401), затем реальное подключение Android/WSS, не только HTTP.

## Токен и подключение APK

При первом запуске gateway создаёт `~/.pi/agent/pi-mobile/device-token`; папка0700, файл0600. На Mac скопировать без вывода в терминал:

```sh
pbcopy < "$HOME/.pi/agent/pi-mobile/device-token"
```

На Linux безопасно перенести секрет лично на свой телефон, не через публичный чат/issue/лог. Не добавлять токен в URL. Установить APK из GitHub Releases, в настройках указать URL и токен именно этого хоста. Если Android отказывает в обновлении из-за другой подписи, не удалять приложение вслепую: сначала сохранить параметры подключения; удаление сбросит защищённые настройки.

После установки расширения новые Pi подключаются автоматически. В уже открытом Pi выполнить `/reload` **вручную и только в свободном состоянии**, затем `/mobile status`. Не отправлять тестовые промпты рабочим агентам. Для проверки достаточно появления правильной сессии в каталоге и чтения её истории.

## Обновление с 0.4 / тестовой 0.5.0

1. Сохранить незакоммиченные локальные изменения; `git pull --ff-only`, `npm ci`, `npm test`.
2. Перезапустить gateway:
   - Mac: `launchctl kickstart -k "gui/$(id -u)/ru.billyhargrove.pi-mobile"`.
   - Linux: `systemctl --user restart pi-mobile.service`.
3. Установить APK0.5.1 поверх предыдущей с той же подписью.
4. Дождаться завершения текущих Pi-задач и выполнить `/reload` в нужных терминалах. **Перезапуск gateway сам не перезапускает Pi.**
5. Проверить каталог. Новые/закрываемые вкладки и удаление истории обслуживает gateway; `$`/MCP/name/live-effort зависят также от версии загруженного расширения.

При сетевом обрыве нет автоматического повтора команд. Ответ «результат неизвестен» — повод проверить Orca, а не многократно нажимать «Создать». Приватные `resume-intents.json` и `new-session-intents.json` не удалять для обхода защиты без проверки процессов.

## Управление

- «+» пространства → подтвердить новый Pi. Вкладка настоящая; промпт не отправляется. Если Pi ожидает trust/approval, ответить на компьютере.
- Свайп живой сессии влево → подтвердить закрытие **одной панели**, не всей группы сплитов. Работающий процесс будет прерван; история сохраняется.
- История → выбрать диалог и подтвердить возобновление. Свайп истории → отдельное подтверждение **безвозвратного удаления файла**. Нет корзины/Undo. Живую сессию сначала закрыть.
- Queue — сообщение после текущей задачи; Steer — вмешательство на ближайшем поддерживаемом шаге. Выбор режима сам ничего не отправляет.
- Effort применяется к последующим запросам текущего Pi; модель меняется только в idle. Старое расширение может запрещать effort во время работы до `/reload`.
- «+» в composer открывает системный выбор любых файлов, не только картинок. До3 вложений /10MiB суммарно. Файлы сохраняются в `~/.pi/agent/pi-mobile/uploads`; инструменты Pi получают реальные локальные пути. Квота256MiB; удалять вручную только больше не нужные файлы, не вложения активных задач.
- При пустом composer кнопка отправки становится микрофоном. Разрешить микрофон, нажать «Готово» после записи, проверить полученный текст и только затем отправить. При уходе из экрана запись отменяется.

### Локальная диктовка

Используется уже установленный в Orca **Parakeet TDT v3 int8** и родной sherpa-onnx, без копирования модели/ключей, сетевого STT или изменения настроек Orca. Это отдельный короткоживущий worker relay, а не внутренний paired-mobile RPC Orca. Запись PCM16 mono16kHz ограничена60 секундами, распознавание90 секундами и2 CPU-потоками. Результат — только текст в поле ввода, не промпт агенту.

На Mac стандартные пути обнаруживаются автоматически: `/Applications/Orca.app/Contents/Resources/node_modules/sherpa-onnx-darwin-arm64/sherpa-onnx.node` (на Intel — darwin-x64) и `~/Library/Application Support/Orca/speech-models/parakeet-tdt-0.6b-v3-int8`. Сначала скачать/подготовить модель средствами Orca, если её ещё нет.

На Linux или при нестандартной установке добавить в окружение relay абсолютные пути `PI_MOBILE_SPEECH_MODULE` (нативный `sherpa-onnx.node` из установленной Orca) и `PI_MOBILE_SPEECH_MODEL_DIR` (папка с `encoder.int8.onnx`, `decoder.int8.onnx`, `joiner.int8.onnx`, `tokens.txt`). Для systemd — `systemctl --user edit pi-mobile.service`, секция `[Service]`, строки `Environment="…=…"`, затем daemon-reload/restart. AppImage-пути должны быть постоянными, не исчезающим mount. Автоматического скачивания/установки движка relay не делает; неподготовленный хост возвращает явную ошибку.

## Диагностика

- **401:** URL/токен относятся к разным хостам, опечатка или токен отозван.
- **Есть HTTPS, нет чата:** проверить WebSocket proxy, префикс пути, состояние Orca и `/mobile status`.
- **«Требуется расширение»:** обновить только свободный Pi; gateway не управляет неизвестным процессом вслепую.
- **Запуск/удаление заблокированы:** incomplete inventory, неизвестные владельцы, прошлый неопределённый запуск. Сначала проверить Orca и логи, не удалять lock/intents наугад.
- **Не видна архивная сессия:** нужны локальное известное пространство, стандартное Pi-хранилище и сохранённые сообщения; служебные subagent-сессии фильтруются.

Смена токена: заменить файл случайным секретом ≥32 символов с правами0600, перезапустить gateway, обновить доверенные телефоны. Удаление сервиса не отзывает опубликованный секрет само по себе.
